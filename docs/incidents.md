### 事故 1：知识库文件"记录已同步"但检索查不到

**现象**
上传了"机器人保养知识.txt"和"故障.txt"，重启多次，问相关问题
始终回答"知识库中没有相关内容"。但侧边栏明明显示这两个文件存在，
file_records.json 也显示它们已经同步。

**排查过程**
1. 先怀疑检索代码 → 直接跑 retriever.invoke() 测试，
   发现检索本身工作正常，能返回结果 → 排除检索层问题
2. 检查向量库实际内容 → 用 vector_store.get() 列出所有片段的
   source 字段，发现库里只有 4 个文件，缺的正是那两个
3. 对比 file_records.json 与实际库内容 → 记录里有 6 个文件，
   库里有 4 个 → 确认是"记录与实际不一致"
4. 追代码找原因 → 同步逻辑的跳过条件是
   `if old_md5 == file_md5` —— 只要记录里的 MD5 没变就跳过，
   从不检查库里是否真的有这个文件
5. 定位到根因：某次同步被中断（只嵌了 2 个文件就停了），
   但记录已经被写入 → 形成死锁，永远跳过、永远补不上

**根因**
同步的"是否更新"判断只信任 file_records.json，不校验向量库实际状态。
记录与库一旦不一致（中断、路径漂移、库被重建等都会导致），
系统无法自愈。

**修复与验证**
在跳过判断中增加库内容校验：先查出库里实际存在的 source 集合，
只有"MD5 未变 **且** 库中确实存在该文件"才跳过。
验证：删除记录文件重新同步后，6 个文件全部入库，相关问题能正常回答。

**经验**
缓存/记录类数据不能作为唯一事实来源——判断状态时必须回到
真实数据源核对。


### 事故 2：向量库索引损坏

**现象**
应用启动时报错：

```
chromadb.errors.InternalError: Error executing plan:
Error loading hnsw index
```

SQLite 里明明有 436 条向量数据，但检索全部返回空。

**排查过程**
1. 直接查询 SQLite → 确认 436 条数据物理存在 → 排除"数据丢失"
2. 用 Chroma 原生客户端（绕过 LangChain）查询 → count() 返回 436，
   但取不到内容 → 数据在，索引读不出来
3. 检查索引文件目录（HNSW 段目录）→ 文件存在，
   但读取时报索引加载失败 → 确认是**索引文件损坏**
4. 回忆操作时间线 → 全量重嵌入（重建库）时，**应用进程并未完全退出**，
   界面窗口关掉后进程仍在后台运行
5. 定位根因：两个进程同时读写同一个 Chroma 数据库

**根因**
Chroma 是**嵌入式数据库**——没有独立服务端进程，每个使用它的
Python 进程直接操作同一批文件。两个进程同时写入时（一个在重建
索引，另一个在响应网页请求），HNSW 索引文件被写成半截状态，
无法加载。

**修复与验证**
1. 彻底关闭所有应用进程（确认无残留）
2. 删除损坏的向量库目录和同步记录
3. 重启应用触发全量重建
4. 验证：`vector_store.get()` 条数正确、`similarity_search`
   能正常返回、应用能回答知识库问题

**经验**
嵌入式数据库没有并发保护，**任何重建/迁移操作前必须先确认
所有使用它的进程已完全退出**——关闭界面窗口不等于关闭进程。


### 事故 3：.gitignore 规则误伤知识库源文件

**现象**
排查事故 1 时，试图从 git 恢复被覆盖的 file_records.json，
git 报错：

```
error: pathspec 'backend/data/file_records.json' did not match
any file(s) known to git
```

检查 `git ls-files` 后发现：`backend/data/` 下的**全部文件**
（6 个知识库 txt、file_records.json）**从未被版本控制追踪**。

**排查过程**
1. 确认 git 报错的含义 → 文件不在版本控制中，不是路径写错
2. 运行 `git ls-files` 列出所有被追踪的文件 → backend/data 下的
   文件全部缺失
3. 检查 `.gitignore` 规则 → 发现一条 `data/`
4. 理解规则语义 → `.gitignore` 中 `data/`（末尾带斜杠、无前导斜杠）
   匹配**任何位置**名为 data 的目录，`backend/data/` 也被一起忽略

**根因**
`.gitignore` 规则 `data/` 是为了忽略项目根目录的临时 data 目录，
但它同时匹配了 `backend/data/`——把最核心的知识库源文件
全部排除在版本控制之外。被忽略的文件不会出现在 `git status`
中，问题完全隐藏，几周都不会被发现。

**修复与验证**
1. 规则改为 `/data/`（前导斜杠 = 只匹配项目根目录下的 data）
2. 用 `git check-ignore <路径>` 逐个验证：
   - `backend/data/chroma_db` → 仍被忽略 ✓
   - `backend/data/洗涤养护.txt` → 已纳入追踪 ✓
3. 提交：知识库源文件正式进入版本历史

**经验**
`.gitignore` 规则必须精确，`data/` 与 `/data/` 语义完全不同。
防御方法：写完规则后用 `git check-ignore` 验证"该忽略的忽略了、
不该忽略的没被忽略"——`git status` 不会为被忽略的文件报警，
问题只会在你需要它的时候才暴露。
